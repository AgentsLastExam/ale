# 0006 — Opaque task identifiers, symmetric stages, kits

**Status**: accepted (2026-07-25)

## Context

Three problems surfaced while preparing to convert a large legacy task corpus.

The previous framework derived data locations from a task's path
(`E:\agenthle\<domain>\<task>\<variant>`) and wrote those paths into prompts. Renaming a
domain therefore touched cached data, sandbox layout and instruction text at once. Any
identifier the framework *parses* becomes an interface, and interfaces resist renaming.

The task manifest also declared setup steps as a tagged union (script, assets, kit)
while verification declared nothing, even though verification needs exactly the same
things — its own data, its own shared code — just later. And scripts were declared at
all, restating in the manifest what the folder layout already said.

Finally, domains share libraries, not shell scripts: a grader protocol, a scoring
toolkit. Those must reach sandboxes whose interpreter we do not choose.

## Decision

**Identifiers are opaque.** A task id is a flat slug derived once from its folder path
(`tasks/demo/hello` → `demo-hello`). The domain and the variant are their own fields;
nothing parses the id. `TaskId` has no accessors, and a lint rule rejects instructions
that mention task- or domain-derived paths.

**Setup and verify are the same shape.** Each is a `StageSpec` naming the assets and
kits it needs. Scripts are not declared: a stage's folder is copied in and its entry
point runs, so the layout on disk *is* the execution semantics. Verify materials are
copied only at verification, which is also what keeps answers out of the agent phase.

**Asset visibility lives with the data.** The domain's asset lock marks a component
`setup` or `verify`. A component marked `verify` can never be staged before the agent,
whatever a task asks for. Central enforcement, because one careless task out of a
hundred and fifty is enough to leak answers.

**Kits are copied, never installed.** A kit is a Python package plus a manifest,
materialised into `/ale/kits/<name>` and put on `PYTHONPATH` for the stage that asked
for it. No pip, no network, no touching the image's package manager — the only approach
that survives an image with Python 3.8 and a conda environment we did not build. Kits
that need image-provided packages declare them and are checked with an import probe.
Versions are content hashes generated by `ale kit lock`; task authors reference a kit by
name and never type a hash.

## Consequences

- Renaming a task or restructuring a domain's folders costs one identifier and one
  registry line. No data moves, no prompt changes.
- The manifest shrank: one union type, one step type and a per-asset stage field all
  disappeared, and the two stages now read as parallel.
- A domain can ship a real library to its tasks, which is the capability that
  distinguishes this framework from harnesses built around per-task scripts.
- Cost: the id is no longer human-parseable, so tooling that wants to group by domain
  reads the field. That is the intended direction of the dependency.
